## Approved preview setup

1. Get approval for an isolated Firebase project and a preview deployment. Use a separate Firestore database, authorised test accounts and independent provider credentials where available. Use the repository's rules and indexes and wait for enabled composite indexes. Turn on Firebase Email/Password and Google only if needed. Add the preview and final site hostnames to Firebase Authentication Authorised domains. The default Google OAuth redirect is the configured Firebase auth domain followed by /__/auth/handler. Verify the actual callback and email-action domains in Firebase and Google OAuth settings. Keep APP_URL and client API origin aligned.
2. Configure public build variables VITE_FIREBASE_API_KEY, VITE_FIREBASE_AUTH_DOMAIN, VITE_FIREBASE_PROJECT_ID and VITE_FIREBASE_APP_ID. For push, also set VITE_FIREBASE_MESSAGING_SENDER_ID and VITE_FIREBASE_VAPID_KEY to the matching web app and public VAPID key. Keep VITE_API_URL unset when API and frontend share an origin.
3. Configure server APP_URL, FIREBASE_PROJECT_ID, CRON_SECRET of at least 32 characters, and Firebase Admin credentials via the hosting identity or FIREBASE_SERVICE_ACCOUNT_JSON. GOOGLE_APPLICATION_CREDENTIALS is a server-local file option. Disable USE_EMULATORS and VITE_USE_EMULATORS outside local tests. Use TRUST_PROXY only for the verified proxy topology. Optional EXCHANGERATE_DEV_API_KEY enables intraday fetches; RATE_MONITOR_INTERVAL_MINUTES defaults to 30. Optional DIGEST_SECRET of at least 32 characters enables digest scheduling. Keep all secrets in the host's secret settings.
4. Email delivery defaults to off. To enable it, configure Gmail with an app password or Resend with a verified sender. Test delivery with an approved inbox before inviting users.
5. Configure an approved external scheduler or worker for authenticated POST /api/jobs/monitor every 5–15 minutes with CRON_SECRET in the Authorization bearer header. Keep secrets out of URLs and logs. Hobby cron's daily cadence cannot meet this. Observe lastCompletedAt, rate failures, backlog age, 429s, repeated attempts and review_required jobs. At load, the serial alert scan and sends can consume the function's 300-second ceiling; run capacity tests before inviting traffic. Watch Firestore reads, writes, and provider budgets. [Vercel cron limits](https://vercel.com/docs/cron-jobs/usage-and-pricing) · [Vercel fair use](https://vercel.com/docs/limits/fair-use-guidelines)

## Approved live delivery checklist

- Email: After explicit send approval, sign into the isolated preview with one verified address you control. Enable email alerts and create one in-range alert with immediate notification enabled, or wait for the scheduler on a normal target. Confirm one provider acceptance, one queue record and one inbox message. Check HTML, plain text, source and timestamps. Rerun the scheduler and confirm no second message. Exercise rejected recipients and retry behavior only with mocks or a provider test environment. Opt in to a summary in the test project, wait for or arrange a due run there, then use the signed link and verify future summary suppression.
- Push: On Chrome Android, install with the browser/app action. On iOS 16.4 or later, use Safari share and Add to Home Screen, then open the installed app. On each device verify standalone mode, sign-in after relaunch, no permission prompt on page load, Allow after tapping Enable, and useful handling after Deny. Enable both devices on one test account. Save a push alert on the test project, close both apps, and confirm one notification per device with a generic preview. Tap it from each device and confirm navigation to the right alert. Disable one device and confirm only the other receives a new test alert. Test a revoked token, app update and offline fallback. [Apple Web Push requirements](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers) · [Firebase web messaging](https://firebase.google.com/docs/cloud-messaging/web/get-started)
- Launch gate: Complete the preview checks, final legal copy and targeted accessibility and Lighthouse checks. Confirm hosting-plan eligibility, approve rollout and rollback scope, and only then deploy with the documented environment. Check the public routes and scheduler again on the approved production release.
